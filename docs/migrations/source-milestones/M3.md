## Người chơi sử dụng được

- Khi tạo/vào phòng từ UI, server tạo hoặc nhận diện một hồ sơ local bền vững bằng token profile ngẫu nhiên. Token này khác token khôi phục ghế; ghế cũ vẫn dùng được sau restart.
- Đổi tên/avatar cập nhật cùng hồ sơ, không tạo ví mới. Không có API tìm hồ sơ theo tên/playerId.
- Trang chủ hiển thị hồ sơ, chip khả dụng/đang giữ/trong bàn, lịch sử sổ chip, nhiệm vụ hằng ngày và trạng thái server local.
- Hồ sơ mới nhận đúng 1.000 chip qua giao dịch mở đầu duy nhất. Không có endpoint cho client tự đặt delta số dư.
- The Gang và UNO vẫn vào/chơi khi ví ít hoặc hết chip vì cả hai là game Giải trí và không dùng wallet.
- Khi một kết quả hợp lệ được commit qua trạng thái phòng, server ghi match/snapshot và tiến độ nhiệm vụ trong cùng transaction SQLite; sau commit mới phát `match_completed`.
- Nhiệm vụ tutorial `tutorial-verified` hiện bị khóa. Client gửi một cờ hoàn thành không thể nhận thưởng vì chưa có bước xác minh tutorial do server điều khiển.

## Lưu trữ và quyết định kỹ thuật

- Runtime hiện tại đã kiểm tra: Node `v24.14.0`. Dùng `node:sqlite`/`DatabaseSync` tích hợp sẵn từ Node 22.5+, không thêm native dependency và không nâng Express/Socket.IO. `package.json`/lock yêu cầu Node `>=22.5.0`.
- Database mặc định là `data/gang.sqlite`; có thể đổi bằng `GANG_DB_FILE`. Phòng/game hiện có vẫn giữ adapter `data/rooms.json` qua `GANG_DATA_FILE` để không làm hỏng reconnect The Gang/UNO.
- Migration SQLite có version 1–2, chạy lại an toàn qua `schema_migrations`. Có bảng `players`, `player_sessions`, `rooms`, `room_members`, `matches`, `match_snapshots`, `wallets`, `wallet_operations`, `wallet_ledger`, `reservations`, `wallet_positions`, `mission_definitions`, `mission_progress`, `mission_claims`, `mission_events` và audit/migration metadata.
- Token profile/ghế được hash SHA-256 trước khi lưu; token raw chỉ ở response/client local storage trong phiên cần thiết, không ghi vào log. Khi migration thành công, snapshot `rooms.json` được backup và bản vận hành được ghi lại không chứa token raw.
- Nguồn migration cũ được đọc trước, copy backup trước import và không bị ghi đè nếu JSON hỏng. Người chơi cũ được map theo ID hiện có, không gộp theo nickname. Token ghế cũ được hash vào `player_sessions`, lịch sử/match cũ giữ dưới `source=rooms-json-v1`.
- Kỳ ngày dùng `Asia/Ho_Chi_Minh` trên server và lấy từ `endedAt` của event, nên kết quả sát nửa đêm không bị tính theo đồng hồ client.
- Thưởng daily chưa nhận được giữ trong 7 kỳ gần nhất để người chơi thấy đúng kỳ và có thể nhận sau; lịch sử claim vẫn độc lập theo `profile + mission + definition version + period`.
- Các nghiệp vụ ví đã có service nội bộ cho grant mở đầu/thưởng, giữ, giải phóng, buy-in, chuyển stack → pot. Ledger nội bộ có delta 0 cho chuyển vị trí để đối soát không tạo chip mới. Settlement cụ thể của Tiến lên/Poker để M4/M5.

## File chính

- `src/platform/persistence/sqliteStore.js` — mở DB, PRAGMA, migration, transaction, backup/integrity.
- `src/platform/profileService.js` — hồ sơ/session, migrate `rooms.json`, đồng bộ room/member/match/snapshot.
- `src/platform/walletService.js` — giới hạn chip, idempotency, ledger, reservation, stack/pot.
- `src/platform/missionService.js` — định nghĩa version, period theo múi giờ server, progress/replay/claim nguyên tử.
- `src/platform/roomService.js`, `src/gameEngine.js` — nối profile ổn định, hash token ghế, sync SQLite trước broadcast.
- `src/httpServer.js` — `/api/profile`, `/api/missions`, `/api/storage/status` và truyền profile token vào socket room flow.
- `public/index.html`, `public/js/portal.js`, `public/css/portal.css` — hồ sơ/ví/nhiệm vụ dùng được từ trang chủ.
- `test/m3.test.js` — test DB tạm thật, migration, atomicity, replay và claim.

## Backup/restore/rollback

1. Dừng `npm start` trước khi sao lưu. Copy `data/rooms.json`, `data/gang.sqlite` và nếu tồn tại thì cả `gang.sqlite-wal`/`gang.sqlite-shm` sang thư mục backup có timestamp. Migration tự tạo thêm `rooms.json.m3-backup-*` trước import.
2. Khôi phục bằng cách dừng server, đặt lại đúng cặp `rooms.json` + SQLite backup cùng thời điểm, rồi chạy `npm start`. Kiểm tra `GET /api/storage/status` và đối soát ledger trước khi cho người chơi vào.
3. Nếu SQLite lỗi, giữ nguyên file lỗi để forensic; không xóa hoặc tự cấp bù. Restore bản backup cùng hoặc cao hơn `schema_migrations` mà code đang hiểu.
4. Không chạy code cũ trực tiếp trên database mới. Rollback code chỉ hợp lệ khi hiểu cùng schema; rollback về adapter JSON cần một bản export compatibility riêng, không được xóa ledger để “khớp” số dư.

## Chưa xác minh / giới hạn

- Chưa có game Kịch tính playable ở M3, nên chưa có settlement buy-in/pot thực tế từ UI; các primitive ví đã được test trực tiếp trên SQLite để M4 dùng.
- Chưa mở thưởng tutorial vì chưa có xác minh server-side thực chất.
- Chưa kiểm tra điện thoại thật, WiFi thật, Safari/Edge thật, crash process thật hoặc luật chính thức của các game chưa phát hành. Browser/socket hiện có là hồi quy tự động trong môi trường Node/Chrome của dự án.
- Node `node:sqlite` vẫn phát cảnh báo experimental trên runtime hiện tại; giới hạn Node đã ghi rõ và không thêm thư viện native để tránh khác biệt build. Nếu máy triển khai dưới Node 22.5, server phải được nâng runtime trước khi chạy M3.

## Đầu vào cho M4

- Game có chip phải gọi `WalletService.reserveMany`/`buyIn` với operation key ổn định, đưa kết quả và snapshot vào cùng transaction, chỉ broadcast sau commit.
- Dùng `profileId` làm chủ sở hữu ví; không dùng socket ID, nickname hay The Gang rank chip. Kiểm tra `canEnterWalletRoom` để một profile không giữ hai bàn có chip.
- M4 cần thêm luật/variant cụ thể, max-loss reservation và settlement; không mở bằng một game giả chỉ để thử ví.
